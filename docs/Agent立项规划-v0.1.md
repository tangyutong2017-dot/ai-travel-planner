# Generation Agent 立项规划 v0.1

> 2026-08-12 · 本文档的技术选型结论**全部来自实测**，不是经验判断。
> 复现脚本见 `backend/scripts/`。

---

## 1. 目标

把用户在向导里填的结构化输入 + 自由文本，变成一份**时间上跑得通、地理上不折返、信息可核实**的多日行程。

### 1.1 验收标准

**硬约束（4 条，全部可程序化校验，违反即判定输出不合格）**

| # | 约束 | 校验方式 |
|---|---|---|
| 1 | 时间闭合：Σ停留 + Σ通勤 + Σ用餐 ≤ 当日可用时长 | `durationMin` + `transitMinutes` 求和 |
| 2 | 同日地点地理集中，不跨片区折返 | 坐标两两距离 |
| 3 | 营业时间不冲突 | 高德 `open_time` |
| 4 | 跨天不重复景点 | 自查 |

**软偏好（5 条）**：每日条目数符合 pace · 三餐在当时所在片区 · 兴趣全覆盖 ·
首末日考虑到达与返程 · 雨天优先室内

> 预算相关约束已于 2026-08-11 移除，理由见 `未来可能做的事.md`。

## 2. 实测记录

五轮实验，每轮只在前一轮基础上改动少数变量。目的地统一为大理 3 日、
同一份用户画像（2 大 1 小、慢节奏、低体力、不吃辣、想看洱海日落）。

### 2.1 第一轮：模型对比（无联网，schema 含 `start` 与 `transit`）

| 指标 | deepseek-v4-pro | deepseek-v4-flash |
|---|---|---|
| 生成耗时 | 121 s | **98 s** |
| tokens | 6,800 | 12,547 |
| 地点可在高德查到 | 6/11 | 6/9 |
| 同日最远两点 | 24.7 km（跨湖折返两次） | **9.9 km** |
| 通勤低估 50% 以上 | 2/4 段 | 2/3 段 |
| 遵守「慢节奏」 | ✗ 第 2 天 6 站 11.5 h | ✓ 第 2 天 5 站 8h45m |
| 覆盖返程 | ✗ | ✗ |

**结论：选 flash。** 更快、更便宜，本次质量还更好。样本量为 1，不宣称 flash 普遍更强，
只说明 pro 在此任务上无可见优势。

**通勤时间必须走地图 API。** 两个模型以同样方式犯同样的错（都低估），说明这不是模型
能力问题而是任务性质问题——LLM 没有路网数据，只能凭感觉且系统性偏乐观。
最严重一例：声称 5 分钟，实际 100 分钟。

### 2.2 第二轮：耗时归因

**吞吐恒定在 112~120 tokens/s，与模型档次无关。** 因此耗时 ≈ 输出量 ÷ 吞吐。

同模型、同需求，仅从 schema 删去 `start` 与 `transit_from_prev_min` 两个字段：

```
98 秒  →  21.9 秒     输出 ~12000 → 2445 tokens
```

**这两个字段本就不该由 LLM 产出**——具体时刻会与真实通勤矛盾，通勤时间系统性低估。
删掉它们既消除一整类错误，又带来 4.5 倍提速。

> 更正：本文档早期版本曾写「换模型解决不了速度」。该结论错误——速度问题不在模型，
> 在输出量，而输出量是可控的。

### 2.3 第三轮：候选池接地（否定结果）

假设「把真实地点摆进上下文能减少模型回忆负担、从而加速」。用高德拉 13 个候选 POI
塞进 prompt 做对照：

| | 耗时 | 输出 tokens | 推理 tokens |
|---|---|---|---|
| A 无接地 | 21.9 s | 2,445 | 1,626 |
| B 给 13 个候选并要求只从中选 | **53.4 s** | 6,406 | **5,917** |

**假设不成立，且方向相反。** 强制从小候选池中选择反而加重推理负担（+264%）。
该实验只否定了「地名清单接地」，未否定「攻略内容接地」——两者机制不同。

### 2.4 第四轮：接入联网搜索（首次，失败）

给模型 Tavily `web_search` 工具，同时改写 prompt 要求覆盖城际交通并新增 `note` 字段。

```
总耗时 121.4 s（LLM 90.7 + 搜索 30.7）  搜索 8 条
输出 11,192 tokens（推理 9,627）
地点存在性 1/15   ← 失败
```

**失败原因是 prompt 回归，不是搜索。** 模型把 `name` 当成「这一行要展示什么」来写：

```
✗ 午餐（免辣）          ✗ 大理古城酒店（入住）      ✗ 大理古城漫游（人民路）
```

这些是行程行描述，不是可检索地名，高德自然搜不到。

**但搜索本身产出了别处拿不到的信息**，包括一条交叉验证才能发现的矛盾：
生态廊道观光车夏季运营至 **19:00**，而 9 月初日落约 **19:35** —— 看完日落就没车了。

### 2.5 第五轮：`name`/`label` 分离 + 搜索并发（达标）

两处改动：prompt 中把「可检索地名」与「展示文案」拆成两个字段并给出正反例；
`web_search` 由串行改为线程池并发。

| | 第四轮 | **第五轮** |
|---|---|---|
| 地点存在性 | 1/15 | **6/6** |
| 总耗时 | 121.4 s | **67.2 s** |
| └ 搜索 | 30.7 s | **8.7 s** |
| └ LLM | 90.7 s | 58.4 s |
| 输出 tokens | 11,192 | 6,573 |
| 推理 tokens | 9,627 | 5,207 |
| 同日最远两点 | 无法计算 | 12.1 km ✓ |

**格式清晰不只提升准确率，还提速。** 字段各归其位后模型不再反复斟酌措辞，
输出量降了 41%。

### 2.6 第六轮：西藏 5 日（长行程 + 高原压力测试）

换目的地与人群：2 位成人、成都飞拉萨、首次进藏有高反顾虑、想看纳木错与布达拉宫。

```
总耗时 135.2 s（LLM 128.1 + 搜索 7.1）   搜索 6 条
输入 13,703   输出 16,484（推理 14,666）
地点存在性 10/13
地理离散 D1 1.6km · D2 4.8km · D3 22.9km · D4 4.0km   全部合格
```

**质量达标，且抓到了两条决定行程成败的信息：**

- 布达拉宫：旺季 200 元，**需提前约 10 天**在「布达拉宫票务预订系统」小程序实名预约
- 纳木错：门票+观光车约 255 元，需在「遇见纳木错」小程序预约、**分时段限量入园**

漏掉任一条行程即作废，而高德给不了、模型记忆未必可靠。**这是联网价值最硬的证据。**

高原安全处理也超出预期：第 1 天只排 3 站留出适应期、推荐供氧酒店、
那根拉山口标注 5190 米并提示不适时缩短停留、主动给出「改为纳木错两日游宿当雄」的降级方案。

**问题一：耗时超线性增长。**

| | 大理 3 日 | 西藏 5 日 | 增幅 |
|---|---|---|---|
| 天数 | 3 | 5 | +67% |
| 总耗时 | 67.2 s | 135.2 s | **+101%** |
| 推理 tokens | 5,207 | 14,666 | **+182%** |

推理开销增长快于天数。按此趋势 7 日行程约需 200 秒以上。
**产品上需限制天数上限，或对长行程分段生成。**

**问题二：地名错字导致检索失败。** 3 个失败中 2 个可修：

| 模型输出 | 问题 | 改写后 |
|---|---|---|
| 药王山**照**景台 | 错别字 | 药王山**观**景台 → 命中 |
| **纳木错**扎西半岛 | 多余前缀 | 扎西半岛 → 命中 |
| 光明港琼甜茶馆 | 高德确实未收录 | 无解 |

不是幻觉，是拼写与冗余前缀。**产品化需加地名变体重试**——`amap.py` 已有
`keyword_variants` 与 `is_plausible_match` 基础，接上可把存在性从 77% 提到 92%。

### 2.7 旁证：人工基准

用同一份需求，由 Claude（本会话）手工完成同一任务作为参照：

```
耗时 166 秒   工具：WebSearch ×3 + 高德 search_poi ×8
地点存在性 7/8
```

**并不比 flash + 搜索（67 秒）快。** 这说明「某些 agent 感觉更快」多半来自流式输出——
用户几秒就看到文字在动，而非总耗时更短。

## 3. 接入后的实测

前六轮全部停留在脚本阶段——验的是「模型输出质量」，一行产品代码都没验过。
接入生成链路后暴露的问题，性质与前六轮完全不同。

### 3.1 精确时刻是错误的抽象（净删 105 行）

时间轴原先由代码推算 `startTime`：起始时刻按节奏拍定，再累加模型估的停留时长
与高德实测通勤。**四个输入里三个是估计，累加结果却以精确到分钟的样子呈现。**

更糟的是它会算出语义上的错误。实测产出过一条 **「14:59 罍街夜市」**——
夜市下午三点去。「夜市该晚上」是语义判断，模型天生就懂；时刻是算术，算术不懂。

改为 `timeSlot`（清晨/上午/中午/下午/傍晚/晚上）后：

| 删除 | 连带消失的 bug |
|---|---|
| cursor 累加与移动条目状态机 | 重复计时 |
| `DAY_START_BY_PACE`、`_hhmm` | 起始时刻怎么定 |
| 前端 `endTimeOf` | — |
| `startTime` 字段及四处渲染 | 排到凌晨、夜市下午去 |

**四条硬约束里的「时间闭合」没有丢**，只是不再需要时钟——`Σ停留 + Σ通勤`
与每日可用时长比对即可。（该字段后续因无处展示而移除，见 5.2。）

高德真实通勤同时**从「时间轴的承重结构」降级为「一条展示信息」**：
算错了不再连锁污染整条时间轴。这是稳定性的实质提升。

### 3.2 地名核实需要三层递进

每层都对应一个实测失败样本：

| 层 | 失败样本 | 根因 |
|---|---|---|
| 1 精确查询 + 变体 | — | 去目的地前缀、去括号说明 |
| 2 模糊比对（双向包含 + 相似度，阈值 0.5） | `双廊古镇漫步（海街·观景平台）` | `amap.is_plausible_match` 只做单向包含（查询词 ⊂ 结果），漏掉了反向情形 |
| 3 子串回退（核心地名头尾 3~4 字） | `药王山照景台`（错字）、`纳木错扎西半岛`（冗余前缀） | 整串在高德返回 **0 个候选**，模糊比对无从下手；但「药王山」「扎西半岛」都能查到 |

阈值取 0.5 而非更宽松：**错误的坐标比没有坐标更糟**——它会让地图画出错误路线、
算出错误通勤。6 个真实失败样本单测全部命中。

### 3.3 住宿片区：一个字段解决三个问题

模型给片区（不给具体酒店——无法核实空房与价格），高德定位后成为该日起点锚：

1. 每天第一站能算通勤（此前首站永远没有）
2. 当天首条 `transfer` 能拿到真实时长——实测「合肥市区 → 三河古镇」
   模型估 120 分钟，校正后 52 分钟（返程 46 分钟，往返不对称符合真实路况）
3. 时间轴有了起点基准

比原先设想的「检测跨区移动缺失就插入合成条目」干净：**不改变模型给的行程结构，
只是把隐含的移动显式化**。

### 3.4 跨省误匹配（用户实测发现）

西藏 7 日行程里出现 **「通勤 3246 分钟」（54 小时）**，并把当天占用污染成 117 小时。

根因是高德检索带 `city_limit=false`，会返回指定城市之外的结果。三层匹配的
子串回退把「光明港琼甜茶馆」切成「光明港」——**福州有个光明港**——
于是拉萨市内一段通勤按「拉萨 → 福州」计算。

修法是加地理护栏：命中点须落在目的地中心 400km 内。阈值要同时容纳两类事实——
纳木错距拉萨 250km、日喀则扎什伦布寺 221km 是合理的省内长途，必须放行；
拉萨到福州 2900km 必须拦住。

### 3.5 并发绕过了限流（无稳定复现路径）

`amap.py` 每处调用前 `time.sleep(0.25)`，但**8 个线程各睡各的，完全挡不住 QPS**。
三层匹配让每个地名最多发 5~10 次检索，并发一打就超限，失败被 `except` 吞掉，
表现为地点**「时好时坏地核实不到」**——同一份行程重跑两次核实率不同。

排查时「色拉寺」单独查成功、批量查失败，正是这个原因。改用锁做全局节流后，
8 个西藏地点 3.2 秒全部命中。

**这个 bug 没有稳定复现路径。** 若非用户盯上 3246 这个离谱数字，
很容易被长期误判成「模型给的地名质量不稳定」。

### 3.6 兜底会掩盖故障

`agent.py` 在生成失败时退回占位行程——初衷是「用户等了两分钟，
给可编辑骨架比一句报错有用」。但副作用是**失败变得无声**。

实测踩过一次：`resolve_stays` 在重构中被误删，界面上看到的是
「AI 生成了一堆占位内容」，很容易误判成模型质量差，真相是 `NameError`——
**agent 根本没跑起来**。

`import` 能通过，因为该函数只在函数体内被调用；Python 的延迟绑定让这类错误
只在运行时暴露。这也是每次改完都要跑真实链路、而非只看 import 与编译的原因。

兜底保留，但改为同时 `logger.exception` 记录完整堆栈。

### 3.7 测试不该依赖真实 LLM

接入后冒烟测试从秒级变成单次 2 分钟并消耗 API 额度。但这些断言验的是
**API 契约与数据流**，AI 质量归 `scripts/` 下的专用脚本管，两者不该耦合。

加 `SKIP_AI_GENERATION` 开关后回到 **3.5 秒 / 51 项全通过**。

## 4. 架构

```
结构化输入（规则换算）+ customText（原样交给模型理解）
        ↓
LLM 一次产出全部天数的计划骨架，可调用 web_search（最多 3 轮，批量并发）
   给：name（可检索地名，无对应地点时留空）+ label（展示文案）
       + type + time_slot + duration_min + reason + note + stay
   不给：市内通勤时间、具体时刻
        ↓
高德批量核实   地名三层匹配（精确 → 模糊 → 子串），带 400km 地理护栏与全局节流
              一次调用即拿到 坐标/地址/图片/门票
高德批量路线   相邻段真实耗时；市内 transfer 用真实驾车时长替换模型估值
高德天气      按真实日期匹配，超出预报范围如实显示「暂无预报」
        ↓
代码：住宿锚定 · 通勤校正 · 结构映射
        ↓
Pydantic 校验 Itinerary → save_itinerary
生成失败退回占位骨架，并记录完整堆栈
```

**接入点**：`app/agent.py` 的 `run_generation_job`。`/generate` 与 `/jobs/{id}` 契约、
前端轮询逻辑均无需改动。

**实测耗时** 60~135 秒，随天数超线性增长（3 日 67s / 5 日 94s / 7 日约 135s）。

**已确定不做**（理由见 `未来可能做的事.md`）：几何层（聚类分天、天内排序）、
结构化 `bookings[]`、单日重新生成、替换景点。

## 5. Prompt 设计

### 5.1 现状

代码库中当前没有生产用 prompt——历史版本（422 行、8 个）随旧 agent 一同删除，
保留在 git `bb07aa4`。第五轮验证用的 prompt 在 `scripts/llm_websearch_test.py`，
产品化时固化为 `app/prompts.py`。

### 5.2 已由实测确定的决策

| 决策 | 依据 |
|---|---|
| **不让 LLM 给通勤时间** | 两模型均系统性低估（最严重 5 分 vs 100 分）；删除该字段还带来提速 |
| **不让 LLM 给具体时刻** | 它给的时刻与真实通勤矛盾；时间轴由代码推算 |
| **`name` 与 `label` 必须分离，并给正反例** | 存在性 1/15 → 6/6 的唯一改动 |
| **「慢节奏」需量化写入 prompt** | pro 把它理解成每天 6 站 11.5 小时 |
| **交通与住宿必须作为条目输出** | 两模型都漏掉返程 |
| **搜索必须并发** | 8 条串行 30.7 s，并发后 8.7 s |
| **时段而非精确时刻** | 代码累加推算的时刻会产出「14:59 逛夜市」这类语义错误 |
| **城际时长交给模型认真估** | 地图算不了航班与高铁；不说明分工边界时模型随手给 60 分钟 |

### 5.3 待验证的假设

- 加入 few-shot 完整示例能否进一步提升质量
- 要求模型输出前自查（每日总时长、是否折返）是否有效
- 长行程分段生成能否解决超线性增长

## 6. 已知风险

### 6.1 搜索引入新的错误源

崇圣寺三塔门票，三次不同搜索给出三个价格：

| 来源 | 价格 |
|---|---|
| Claude WebSearch | 45 元 |
| DeepSeek 第四轮 | 98 元（线上约 73） |
| DeepSeek 第五轮 | 75 元 |

**联网不等于准确**，而且搜索结果带着「我查过了」的可信外观，比模型直接编造更难识破。

处置：价格与时刻类信息统一标注「以现场/官方为准」；prompt 中要求模型给出信息来源。

### 6.2 其他

| 问题 | 处置 |
|---|---|
| 生成耗时 67~135 秒，且随天数超线性增长 | 长行程需限制天数或分段生成 |
| **时间闭合不再有任何检查** | `plannedMinutes` 因无处展示而移除。实测出现过首日占用 14 小时（航班就占 9 小时）、单日六景点两段自驾等偏重安排，现在不会有提示 |
| **模型输出结构不稳定** | 同一输入连跑三次，跨区转移条目分别为「有/漏掉/有」。结构完整性无法靠 prompt 保证 |
| 地名错字/冗余前缀导致检索失败 | 产品化时加变体重试，复用 amap.py 已有的 keyword_variants |
| 公交耗时 | 不接公交接口，全部按驾车估算，UI 需标明 |
| 换宿判定 | MVP 为整趟单一住宿片区，跨区域长线交给用户手动调整 |
