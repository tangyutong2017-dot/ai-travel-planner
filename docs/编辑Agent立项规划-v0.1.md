# 编辑 Agent 立项规划 v0.1

> 2026-08-18。对应 PRD P0「AI 调整输入框」。
> 与 `Agent立项规划-v0.1.md`（生成 Agent）并列，两者共用高德核实链路与 LLM 客户端。

---

## 1. 要解决什么

工作区右侧面板里有这么一句：

> 缺失项可通过下方 AI 输入框补充或重新生成。

**下方没有输入框。** 这是一句空头承诺，性质与 `未来可能做的事.md` 里记的天气
「临近出发时会自动更新」相同——用确定的语气描述不存在的行为。要么实现它，要么改文案。
本次选择实现。

目标：用户用一句自然语言修改已生成的行程，例如「第二天太赶了，删掉一个景点」。

---

## 2. 核心判断：让 LLM 输出操作，而不是重出行程

| | 重出整份行程 | **只输出编辑操作**（采用） |
|---|---|---|
| 时延 | 与生成同量级，60~135 秒 | **实测 2.7~5.6 秒**（见 3.1） |
| 副作用 | 未提及的部分也会变 | 只动被点名的条目 |
| 复用 | 无 | `update_itinerary_item`、`delete_itinerary_item` 已存在 |

否决「重出行程」的决定性理由不是时延，而是**副作用**。`Agent立项规划-v0.1.md` 3.6 已记录
模型输出存在结构不稳定（`transfer` 条目在多次生成间时有时无）。用户只想换顿午饭，
第三天却被悄悄改了——这类改动没有任何提示，是最难被发现的一种。

这与项目既有的四层分工一致：**LLM 负责判断，代码负责执行**。

---

## 3. 立项前实测

探针：`scratchpad/probe_edit.py`，直接打 DeepSeek API，不改代码库。
样本行程「婺源古村慢游 2 日」，2 天 / 9 条目。模型 `deepseek-v4-flash`（与生成同款）。

### 3.1 时延与用量：比生成快一个数量级

| 指令 | 耗时 | 入 token | 出 token（含推理） |
|---|---|---|---|
| 第二天太赶了，删掉一个景点 | 2.7s | 1487 | 236（99） |
| 把第一天的午饭换成当地特色菜 | 5.6s | 1486 | 582（409） |
| 第二天下午想加一个喝茶的地方 | 4.6s | 1485 | 402（255） |
| 把午饭时间往后挪一点 | 2.8s | 1484 | 251（126） |

生成一次是 60~135 秒，编辑是 **2.7~5.6 秒**。差距来自输出量：生成要吐整份行程
（实测 16,484 token，其中推理占 89%），编辑只吐一两个操作。

**结论：编辑走同步请求即可，不需要 job 轮询那套异步机制。**

### 3.2 上下文塞得下，不需要检索

| | 字符 | ≈token |
|---|---|---|
| 完整行程 JSON | 5477 | 2738 |
| 精简后（仅 id/标题/类型/时段/时长） | 1304 | **652** |

7 天行程精简后约 2300 token。**整份行程可以直接进 prompt**，模型能看到全局，
「第二天太赶了」这类需要跨条目比较的指令才成立。

精简是必要的：地址、坐标、图片 URL、推荐理由对「改哪一条」没有帮助，却占了 3/4 体积。

### 3.3 最重要的发现：prompt 的行动倾向决定这个功能成不成立

同一组指令、同一个模型，只改 system prompt：

| prompt 版本 | 执行 | 反问 |
|---|---|---|
| v1「指向不明时反问澄清」 | **0 / 4** | 4 / 4 |
| v2「默认执行，不要反问」 | **4 / 4** | 0 / 4 |

v1 写的是一句看起来很合理的话——「如果要求指向不明，不要猜，直接反问」。
结果模型对**每一条**指令都反问，包括「第二天下午想加一个喝茶的地方」这种
只是没指定插入位置的要求。四次交互零改动，功能等于不可用。

v2 改成默认执行，并给出理由：**多问一轮的代价高于选错一个条目——选错了可以一键撤销。**
这句话同时解释了为什么回退功能是必需的：**它不只是安全网，它是「敢直接执行」的前提。**

v2 的实际输出（节选）：

```
delete D2 trip_new_34acbfa2_d2_e2995e
回复：已删掉第二天下午的「汪口（可选）· 俞氏宗祠与古商埠」，
      这样第二天只保留篁岭和江湾，节奏更宽松；如果不是这个可以告诉我。
```

选择合理（删的是标了「可选」的那个），并主动交代了选择依据与纠正方式。

### 3.4 id 编造率：8 次调用，0 次编造

两轮共 8 次工具调用，模型引用的 `itemId` **全部是行程中真实存在的**。

但这不构成「可以不校验」的理由——样本只有 9 个条目、id 形如
`trip_new_34acbfa2_d2_e2995e`（长且无规律，不易编造）。条目更多、id 更相似时
仍可能出错。**校验必须做**，只是预期触发率低。

### 3.5 insert 会编造地名——这是 insert 的主要失败模式

指令「第二天下午想加一个喝茶的地方」，模型给出的新增条目标题是
**「汪口茶馆 · 下午茶歇」**。拿项目自己的 `resolve_place` 去核实：

| 地名 | 高德核实结果 |
|---|---|
| 汪口茶馆 | ❌ 失败 |
| 下午茶歇 | ❌ 失败 |
| 汪口 | ✅ 汪口景区 |
| 篁岭 | ✅ 婺源篁岭景区 |
| 江湾 | ✅ 江湾景区 |
| 婺源博物馆 | ✅ 婺源博物馆 |

**真实地名全部命中，编造地名全部被挡。** 核实链路本身是有效的。

结论：`insert` **必须**走 `resolve_place`，核实失败就拒绝执行并如实告知，
不能只存一个名字。否则行程里会出现一个没有坐标、没有地址、地图上不存在的点——
这正是项目一路砍掉预算总额、公交系数所反对的东西。

这也意味着 `insert` 比其他三个操作重得多：它要联网、可能失败、耗时不可控。

### 3.6 自由文本字段的事实性风险（未解决）

「把第一天的午饭换成当地特色菜」，模型把标题改成：

> 婺源县城午餐 · **清明果 / 汽锅鱼 / 糊豆腐**（当地特色菜）

清明果、糊豆腐确是婺源菜，**汽锅鱼是云南菜**。模型往江西行程里塞了一道云南菜。

`title` 和 `reason` 是自由文本，没有任何数据源可以校验。这类错误
**当前方案无法防住**，只能靠用户自己看出来。

记录在此作为已知局限，不作为阻塞项：错误局限在文案层，不影响坐标、路线、地图等
结构化数据；且用户可直接手动编辑标题。

## 4. 操作集契约

四个操作。每个都必须先通过校验才进入执行。

| 操作 | 参数 | 后端现状 | 校验规则 |
|---|---|---|---|
| `update` | day, itemId, 可选 title/timeSlot/durationMin/stopType/cost/reason | ✅ `update_itinerary_item` | itemId 必须存在于该天 |
| `delete` | day, itemId | ✅ `delete_itinerary_item` | 同上 |
| `insert` | day, title, stopType, timeSlot, 可选 afterItemId | ❌ 新写 | 走 `resolve_place`，失败则整条指令拒绝 |
| `move` | itemId, day, toDay, 可选 afterItemId | ❌ 新写 | 两个 day 都要存在；afterItemId 若给出须在 toDay 内 |

字段范围直接复用既有的 `UpdateItineraryItemPayload` 与 `TimeSlot`/`StopType` 枚举，
不新增契约。

**全成功或全不动。** LLM 一次可吐多个操作；只要有一个校验失败，整条指令拒绝执行并说明原因。
部分执行会留下一个用户无法理解的中间状态；而有快照在手，回滚是免费的。

---

## 5. 回退语义

### 5.1 快照，不做逆操作

`ItineraryRecord.days_json` 是**单个 JSONB 列**——整份行程就是一个 blob。
快照 = 复制这一列，5.5KB。

逆操作方案要为每个操作各写一个逆操作：`delete` 得记住被删条目**及其原始位置**，
`move` 得记住旧坐标，还要保证每个逆操作都正确。快照不可能算错。

### 5.2 三条语义决定

**一条指令 = 一份快照**，不是一个操作一份。用户说「删掉两个景点」产生 2 个 delete，
撤销时期望撤销的是**这句话**，不是点两次。

**手动编辑也要快照。** 否则存在这个陷阱：AI 改一次 → 手动改一次 → 点撤销 →
手动那次改动被静默抹掉，用户完全无法预期。既然成本相同，就在所有写操作前统一快照。

**留最近 10 条**（`itinerary_revisions` 表）。只加一列 `previous_days_json` 更省事，
但只能撤一步；连改三次才发现第一次错了是常见场景，而多存几份代价几乎为零。

## 6. 失败模式与处置

| 失败 | 处置 |
|---|---|
| itemId 不存在 | 拒绝整条指令，回执说明「没找到你说的条目」 |
| insert 地名核实失败 | 拒绝，回执如实说「没查到这个地方」（见 3.5） |
| 模型不调工具、只回文字 | 原样把文字作为回执显示——这是澄清或拒答，属正常路径 |
| 模型吐出越界枚举值 | Pydantic 校验拦截，同 itemId 不存在处理 |
| LLM 超时/不可用 | 回执报错，行程不动 |
| 标题含事实错误 | **防不住**（见 3.6），用户手动改 |

---

## 7. 回执由代码生成，不由 LLM 撰写

模型描述的是**它以为自己做了什么**。id 编错、操作被拒，它照样会回
「已把 D2 午餐改为徽菜馆」。

因此回执从**实际执行成功的操作**拼出。模型 `reply` 字段里的话可以作为补充说明，
但「改了什么」这句事实必须由代码陈述。

---

## 8. 不做什么

| 事项 | 理由 |
|---|---|
| 多轮澄清状态机 | 3.3 实测表明默认执行 + 可撤销比反问体验好，且不需要维护会话状态 |
| 重做（redo） | 撤销已覆盖主要需求，重做要再维护一个栈 |
| 改动预览 → 用户确认 | 要维护 pending 操作状态，前后端都要加。有撤销就够了 |
| 单日重新生成、替换景点 | 已在 `未来可能做的事.md` 记录为不做 |

---

## 9. 落地顺序

1. `itinerary_revisions` 表 + 快照/回退函数，并接到**现有**手动编辑路径上
   （先让撤销对已有功能生效，可独立验证，不依赖 LLM）
2. `insert_item`、`move_item` 两个仓储函数 + 校验
3. LLM 层：工具声明、精简序列化、system prompt（用 3.3 的 v2 措辞）
4. `POST /api/trips/{id}/chat`、`POST /api/trips/{id}/undo`
5. 前端：输入框、消息流、改动条目高亮、撤销按钮

第 1 步刻意排在最前——它不依赖 LLM，能单独测，且是第 3 步「敢直接执行」的前提。

---

## 10. 验收标准

- [ ] 四类指令（删/改/加/移）各能一句话完成，端到端 **10 秒内**（实测 2.7~5.6s，留余量）
- [ ] 编造的 itemId 被拒绝且有明确回执，行程不被破坏
- [ ] 编造的地名（如「汪口茶馆」）被高德核实挡下，不落库
- [ ] 撤销能还原 AI 改动**与**手动改动
- [ ] 一条指令产生多个操作时，撤销一次全部还原
- [ ] 部分校验失败时行程完全不动
