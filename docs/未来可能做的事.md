# 未来可能做的事

明确**推迟**而非遗漏的事项。每条写清楚"为什么现在不做"和"什么时候值得做"，
避免以后重新讨论一遍，也避免被误当成缺陷。

---

## 高德公交路线接口

**是什么**：封装高德 transit 路线 API，为选择"公共交通"的用户给出真实公交耗时。

**为什么现在不做**：需要新封装一个接口，且公交换乘的返回结构比驾车复杂得多
（多方案、多段换乘、步行接驳），解析成本高。MVP 阶段先用驾车耗时顶着。

**代价（必须知情）**：市区公交实际耗时通常是驾车的 1.5–2 倍。用户勾了"公共交通"
但拿到的是驾车时长时，**行程会显得比实际宽松**，时间闭合校验也建立在偏低的数字上。

**曾考虑但已否决的权宜方案**：把驾车时长乘经验系数（1.6）冒充公交耗时。
**2026-08-11 决定不采用**——理由与移除预算一致：那个数字既不是驾车耗时也不是
公交耗时，是个没有来源的编造值。宁可承认"当前按驾车估算"，也不要制造精确的假象。

**因此当前的诚实做法**：所有通勤耗时均按驾车计算。若要在 UI 上说明，
应写"耗时按驾车估算"，而不是伪装成公交耗时。

**什么时候值得做**：当"时间闭合"成为用户真实抱怨点时；或者作品集需要展示
多模态交通规划能力时。

## 预算规划

**是什么**：预算区间输入、每日预算分解、预算总表、超支校验。

**为什么现在不做**：已于 2026-08-11 移除。高德 POI 的 `cost` 覆盖率低，
餐饮与交通费用没有可靠数据源，加总出的数字是估算而非事实。一个不可信的
"总预算 ¥3280"比不显示更糟。

**保留了什么**：单个景点的真实门票价（`ItineraryItem.cost`，来自高德），
在卡片上如实展示"免费 / ¥80"，但不加总、不校验。

**什么时候值得做**：接入了可靠的票价/餐饮价格数据源之后。

## RAG 旅游攻略库

**是什么**：检索目的地攻略语料，为规划提供「建议游玩时长、几点去人少、怎么串、值不值得去」
这类高德与 LLM 都给不了的经验性知识。

**为什么推迟（2026-08-11 决定）**：输入层的投入产出比更高。补齐出发城市、城际交通、
同行关系、档次、体力接受度等字段是几天的活，建 RAG 库是几周的活，而前者收益更直接——
DeepSeek 对热门目的地的知识本就够用，输入越充分它发挥越好。

**唯一不可替代之处**：建议游玩时长，这是时间闭合校验的地基。MVP 阶段先用
「LLM 估计 + 按 POI 类型兜底 + 超时等比压缩」顶住。

**什么时候值得做**：当发现 LLM 对目的地的知识明显不足（小众目的地行程质量差），
或时长估计频繁导致校验失败时。

**语料来源的已知难点**：中文高质量旅游攻略的合法公开语料稀缺。马蜂窝/小红书/携程
无公开 API 且爬取有风险；中文维基导游对国内目的地覆盖薄。可行路径是选 3–5 个城市
人工精选整理，而非追求全国覆盖。

## 住宿换宿的收益/成本判定

**是什么**：多日行程中自动决定"住一处还是中途换宿"。设计过一个判定式——
`不换宿代价 = 剩余天数 × 2 × 单程通勤` vs `换宿代价 = 转移时间 + 固定惩罚 P`，
P 用来量化"用户有多讨厌搬家"。

**为什么推迟（2026-08-11 决定）**：P 需要调参，且判定结果不直观、不好解释，
相对收益复杂度过高。MVP 阶段先用最简单的做法——**整趟行程单一住宿片区**，
由行程重心决定；跨区域长线（如云南环线）的换宿交给用户手动调整。

**什么时候值得做**：当用户实际生成跨区域长线行程、且抱怨每天通勤过长时。

## 分批产出（首屏优化）

**是什么**：第 1 天生成完即写库返回，其余天数后台继续，前端轮询补齐。
可把感知时延从约 35 秒压到约 10 秒。

**为什么推迟（2026-08-11 决定）**：需要拆分生成流程、处理部分失败与状态同步，
复杂度高。先做完整生成，等实测时延确实难以接受时再上。

**已有基础**：`DayPlan.generationStatus` 五态、前端 5 秒轮询、"后续天数后台生成"
提示条**都已经在代码里**，真要做时不用从零开始。

## 生成过程可视化（流式）

**是什么**：让用户看到行程逐天浮现，或看到 AI 的推理过程与搜索动作。

**为什么推迟（2026-08-12 决定）**：实测西藏 5 日那次，输出 16,484 token 中
**推理占 14,666（89%）**，真正的 JSON 内容只有约 1,800 token。按 112 tok/s 估算，
约 112 秒在推理、16 秒在输出——**只流式输出 JSON 的话，用户会先盯着空白等两分钟，
然后行程在十几秒内全部涌出**，逐天浮现的效果几乎看不到。

真正有效的做法是流式输出**推理内容**（DeepSeek 的 `reasoning_content`），
让用户看到「正在查布达拉宫预约方式」「考虑到首次进藏，第一天不安排景点」这类过程。
但这需要改造 job 状态模型（现在只有 progress + message 两个标量）与前端渲染，
成本高于当前收益。

**现有替代**：job 轮询 + 五步进度条已能表达阶段推进。

## 2026-08-17 一次性砍掉的功能

以下五项**明确不做**，不是遗漏。共同理由：作品集的价值在于把一条主链路做扎实、
把技术判断讲清楚，而不是功能数量。每加一项都要承担它的维护与出错面。

| 事项 | 原属 | 不做的理由 |
|---|---|---|
| 结构化 `bookings[]` | 输出层设计 | 预约信息已在 `note` 文本里可读，`bookRequired` 角标够用。结构化后要维护 itemId 引用与 UI 列表，收益是「能做倒计时提醒」——而作品集不需要提醒功能 |
| 几何层（聚类分天、天内排序） | Agent 架构 | 实测模型给的顺序地理合格率一直不错（大理 12.1km、西藏四天全过）。加了运筹反而可能打乱它已考虑好的叙事顺序 |
| `分享链接`、`同步日历` 按钮 | 输出页 | 分享要公开只读页与鉴权，日历要 ICS 生成与授权。两者都是独立子系统 |
| 单日重新生成 | PRD P1 | 依赖 Editing Agent，且一次生成 60~135 秒，单日重生成的体验并不比整体重来好多少 |
| 替换景点 | PRD P1 | 需要候选池与替换接口。用户可以手动编辑条目达到同样效果 |

**已保留的替代路径**：手动编辑（改标题/时段/时长/类型/理由）与删除条目均可用，
足以覆盖「这个景点我不想去」「时间想调一下」这类真实需求。

## 其他推迟项

| 事项 | 为什么推迟 |
|---|---|
| 拖拽排序景点 | 交互成本高，手动编辑已能满足调整需求 |
| 后端生成 PDF | 前端 `window.print()` 足够 MVP；后端渲染要引入无头浏览器 |
| 用户登录 / 多设备同步 | 作品集演示不需要，会显著增加复杂度 |
| 分享链接 | 需要公开访问的只读页面与鉴权设计 |
| 和风天气 | 高德天气够用，多一个 key 多一处依赖 |
| Wikidata 景点描述 | 可作为推荐理由的补充语料，属加分项非必需 |
| `smoke_test.py` 改造为 pytest + TestClient | 当前脚本形态可用；进 CI 时再改，需配独立测试库 |
| `@app.on_event("startup")` 换 lifespan | 废弃写法但仍可用，随下次动 `main.py` 时顺手改 |
